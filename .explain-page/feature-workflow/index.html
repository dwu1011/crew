One goal.
The right crew for the work.

A central planner turns your request into owned, verifiable tasks. Small changes take a short route. Larger features get investigation, reviewed specs and groups of agents working toward one release.

Autonomy with consistent completion rules.

Planning depth, task count and group size vary. A small issue can contain its entire spec. Independent verification and evidence of the released outcome remain required; their scope scales with the change.

02 / PROPORTIONAL PROCESS

Three routes, chosen by judgment.

Small / clear

Add a sort option

Existing patterns, localized behavior, clear expected result.

Artifacts: One issue with acceptance criteria and a verification approach.

Participants: Planner for triage, one worker, one independent validator.

No separate design document. A focused regression check and affected user journey may provide the evidence.

Connected / understood

Add team invitations

Several layers and contracts must agree.

Artifacts: Brief spec, reviewed task breakdown, dependencies.

Participants: Planner, relevant design reviewer, workers and validators; integration ownership is explicit.

Split work only where it can be built and tested independently.

Broad / uncertain

Add organization isolation

Permissions, storage and existing behavior interact across the application.

Artifacts: Investigations, versioned spec, design review, task graph and release milestones.

Participants: Planner, relevant specialists, several task groups and independent integration validation.

Resolve consequential uncertainty before dependent implementation starts.

Illustrative classifications, not fixed rules. A one-line permission change can need more scrutiny than a large cosmetic update. The planner records its routing reason and can expand the process when new evidence appears.

03 / THE ENFORCED LOOP

Every task has an owner and an exit condition.

Workers submit work for validation. Validators return reproducible failures or record a pass for the reviewed revision. Blocked work keeps its handoff and resumes after the blocker is resolved. Integration can uncover defects and reopen affected work.

A task carries its own context

Goal, scope, spec revision, acceptance criteria, dependencies, current owner, branch, evidence and next action. A replacement agent can resume from the record.

Evidence controls advancement

The daemon validates claims and transitions. A worker cannot approve its own work. Code or contract changes invalidate affected verification. Repeated failed attempts trigger diagnosis or replanning.

“Integrated” finishes a task’s implementation flow. The feature remains open until its release is verified. A single-task change still gets a proportionate integration check.

Explore independently

For consequential choices, investigators form initial conclusions separately. The planner compares evidence and commissions a focused experiment when opinions conflict.

Delegate with a contract

A group receives an outcome, task scope, dependencies and acceptance criteria. One owner coordinates it. Specialists join for specific questions; the group ends when its work is complete.

Validate independently

A validator derives checks from the spec before reading the worker’s success narrative. Different perspectives improve coverage when they bring separate reasoning and concrete probes.

Central planning does not require central micromanagement.

Workers can resolve local implementation choices and request specialist help. Changes to product intent or acceptance criteria return to the planner for a recorded revision and independent review. Ask you when the decision depends on your preference.

05 / WHAT SURVIVES THE CONVERSATION

The board is a view of durable work.

Proposed storage in Crew

SQLite · coordination truthFeatures, tasks, attempts, claims, dependencies, reviews, releases and transition history.
Versioned artifacts · detailed contextSpecs, decisions and test evidence, referenced by revision from task records.
Messages · notifications and discussionTell agents what changed. Losing a notification does not erase the task.

Each transition leaves a record

task · from → to · actor · time · reason · spec revision · code revision · evidence

State updates and transition records commit together. Claims are exclusive and belong to an execution; recovery fences off a stale execution before assigning a replacement.

Task records survive crew shutdown independently of the existing policy that clears messages. The kanban board shows current state, blockers, ownership and evidence.

06 / CURRENT FOUNDATION → PROPOSED EXTENSION

What exists, and what this adds.

Current Crew

Named seats, managed Claude Code executions, reusable profiles, project runs, durable messaging and delivery recovery.

Proposed next layer

Feature intake, adaptive planning, task claims, temporary groups, independent review gates, isolated workspaces, integration and autonomous releases.

Relationship to your kanban plugin and source notes

The plugin supplies the starting ideas: claimable issues, acceptance contracts, independent validation, rework, worktrees and milestone integration. Crew would add autonomous specification, daemon-enforced actor rules, durable execution ownership and release completion.

The plugin’s “done” can mean a validated PR exists. This proposal tracks integration and deployment separately. Group assignment, routing rules and milestone release batching are proposed design choices, not implemented contracts.
